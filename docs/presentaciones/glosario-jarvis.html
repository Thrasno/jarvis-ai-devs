Los nombres parecidos no implican la misma operación. Esta guía distingue configuración, memoria y flujo de desarrollo; no sustituye la comprobación de una instalación real.

Jarvis y configuración

Jarvis

Ecosistema de apoyo al desarrollo: CLI de instalación y configuración, instrucciones y habilidades para agentes, flujo SDD y memoria Hive. La CLI prepara integraciones y ofrece diagnósticos; no es la base de datos de memorias. Ejemplo: iniciar jarvis para configurar un agente y después comprobarlo con jarvis verify --provider all. Configuración.

Estado deseado y dos archivos

El estado deseado es la configuración de agente registrada para esta máquina que Jarvis puede reproducir, no una descripción de cada archivo que exista hoy. ~/.jarvis/state.yaml guarda el manifiesto de reproducción; ~/.jarvis/config.yaml guarda ajustes de usuario de la CLI, como api_url y correo. Son almacenes disjuntos: no se editan como si fueran el mismo archivo. Ejemplo: cambiar la URL de Hive API en la configuración de usuario no equivale a modificar la lista de habilidades registradas en el manifiesto. Dos almacenes.

Contenido gestionado

Archivos e instrucciones de agente generados desde plantillas, recursos y adaptadores de Jarvis, por ejemplo bloques de protocolo Hive o archivos de configuración de Claude/OpenCode. Si el comportamiento generado falla, se corrige la fuente y se regenera con un flujo de Jarvis; no se arregla editando a mano el archivo generado. Jarvis preserva contenido propio del usuario según la propiedad de cada destino, no mediante una promesa universal de sobrescritura. Artefactos y fuentes.

Memoria: ¿dónde vive?

Hive y hive-daemon

Hive es la memoria local del producto; hive-daemon sirve las operaciones locales. Ejemplo: consultar una decisión del proyecto en la línea de tiempo local con jarvis timeline --project <proyecto>. Funciona con enfoque local-first: la memoria local puede seguir disponible sin conexión al servicio compartido, siempre que el daemon local funcione. Memoria local.

Hive API

Servicio de memoria compartida del equipo, distinto del daemon local. Permite centralizar conocimiento entre miembros cuando se configura la sincronización y los permisos correspondientes. Instalar Jarvis o guardar algo localmente no prueba que ya esté compartido. Sincronización de Hive.

Hive frente a Engram

Hive y Hive API son memoria del producto Jarvis. Engram puede ser memoria del asistente usado durante el desarrollo y no es el almacén Hive del producto. Ejemplo: recordar contexto en una sesión del asistente no demuestra que una decisión se haya guardado en Hive ni que el equipo pueda recuperarla. Límite entre memorias.

Sin garantía implícita: instrucciones, prompts o hooks pueden orientar al agente para guardar o consultar memorias; no prueban que cada guardado o recuperación se haya ejecutado. Compruebe el resultado observado en el sistema correspondiente.

Tres operaciones que no deben confundirse

jarvis sync = reproducir configuración

Reaplica sin preguntas ni flags el estado de agente registrado en ~/.jarvis/state.yaml: asignaciones de modelos, MCP gestionados por Jarvis, habilidades instaladas por el instalador, persona y línea de estado si se habilitó al instalar. No sincroniza memoria Hive. Ejemplo: después de actualizar Jarvis, reproducir la configuración gestionada de esta máquina. Manifiesto · Reglas de reproducción.

jarvis reconcile = reparar desvíos observados

Parte de lo que los diagnósticos observan en el sistema y repara desvíos gestionados de forma segura; no es la reproducción general del manifiesto deseado. Ejemplo: revisar primero reparaciones propuestas con jarvis reconcile --provider all --dry-run. Referencia de CLI.

mem_sync y sincronización en segundo plano = mover memorias

La herramienta de Hive mem_sync solicita sincronización de datos de memoria entre Hive local y Hive API; el daemon puede sincronizar en segundo plano si se habilita explícitamente. Requiere configuración y credenciales de Hive API y disponibilidad del servicio para completar el intercambio. Ninguna de estas operaciones reproduce la configuración del agente. Ejemplo: un equipo habilita auto_sync por separado; trabajar sin red sigue siendo local. Configurar sync de memoria.

Trabajo, presentación y responsabilidades

SDD y la inyección de prompts

SDD es el flujo guiado para pasar de una intención a propuesta, especificación, diseño, tareas, implementación y verificación con artefactos. La inyección de prompts del producto instala instrucciones y capacidades que orientan al agente: no es por sí sola una ejecución completa ni prueba de que se hayan creado o verificado artefactos SDD. Ejemplo: disponer de una habilidad SDD instalada no significa que una tarea ya esté verificada. Guía SDD.

Persona frente a habilidad

Una persona define presentación: idioma, tono y forma de explicar, sin alterar la política técnica. Una habilidad aporta instrucciones para una capacidad o flujo de trabajo. Ejemplo: elegir una voz neutra no instala una habilidad de pruebas; instalar esa habilidad no convierte al agente en responsable del equipo. Perfiles de persona · Habilidades instaladas.

Roles humanos, no personas

Desarrollador: usa y comprueba la integración en su proyecto. Responsable de equipo: acuerda límites de adopción y datos compartidos. Administrador de Hive: opera el servicio local o compartido y su configuración. Evaluador: registra resultados observados y fallos para decidir adopción. Formador: acompaña el aprendizaje y demuestra pasos reales. Son responsabilidades, no voces seleccionables ni capacidades instaladas. Adopción en equipo.

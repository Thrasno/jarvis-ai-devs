# Exploration — issue-493-sync-desired-state-replay

**Date**: 2026-08-13
**Source**: GitHub issue [#493](https://github.com/Thrasno/jarvis-ai-devs/issues/493)
**Method**: Direct code inspection of `jarvis-cli`, plus comparative review of the `gentle-ai` reference implementation at commit `0d85ec05`.

Every claim below is anchored to a `file:line` verified against the working tree. This artifact was written from a completed investigation rather than generated by a fresh exploration pass; the issue body carries the same findings in contract form.

## Question

`jarvis sync` is a legacy no-op that prints a message pointing at `mem_sync`. The change redefines it as the non-interactive command that replays the last installation's desired state using the assets embedded in the currently installed binary.

The investigation had to answer one question before any design was possible: **is the persisted configuration a complete and unambiguous replay manifest?**

Answer: no, but the gap is one field. Three premises in the original issue draft were wrong, and correcting them removed most of the assumed work.

## Findings

### F1 — Jarvis-managed MCP definitions are not a persisted user choice

The wizard appears to configure MCPs, but no user choice reaches persistence:

- `configureWizardAgents` accepts `hiveEntry` and `context7Entry` and discards both immediately: `_ = hiveEntry` / `_ = context7Entry` (`jarvis-cli/internal/tui/agent_setup.go:90-91`).
- Both production call sites pass zero values: `agent.MCPEntry{}` (`jarvis-cli/internal/tui/steps.go:1431`, `jarvis-cli/internal/tui/nontui.go:384`).
- The canonical definitions are constructed from embedded code — the `hive-daemon` binary path and the Context7 URL (`jarvis-cli/internal/agent/native_mcp_recovery.go:61-68`).

Jarvis-managed MCP definitions are fully derivable from the installed version. Nothing about them belongs in a replay manifest.

The `"I ACKNOWLEDGE"` gate (`agent_setup.go:48`, `steps.go:1269`) is a destructive-action confirmation, not a choice: no path continues without it. Because sync only ever replaces Jarvis-managed MCPs and never user-defined ones, sync performs the replacement unconditionally.

### F2 — Project-scoped work does not belong to sync

`refreshProjectRegistryForApply` (`jarvis-cli/internal/tui/agent_setup.go:332-344`) refreshes the skill registry of whichever git worktree the interactive wizard happened to run in. It is a convenience side effect of the interactive command, unrelated to machine-scoped ecosystem state.

### F3 — Skill frontmatter does not decide installation

`Skill.IsCore` and `Skill.Scope` (`jarvis-cli/internal/skills/registry.go:31-37`) are parsed from frontmatter `scope:`, but they do not control installation. The real source is `interactiveSkillIDs` (`jarvis-cli/internal/tui/skills_selection.go:28-33`), populated by three wizard prompts (`skills_selection.go:22-26`): Zoho-Deluge, PHP (`phpunit-testing` + `laravel-architecture`), and Go Testing.

Everything else auto-installs regardless of frontmatter (`skills_selection.go:49-51`):

```go
if !interactiveSkillIDs[s.ID] {
	// All non stack-specific skills are auto-installed.
	selected[s.ID] = true
}
```

Counter-example that makes the trap concrete: `sdd-spec` declares `scope: optional` and is auto-installed anyway. Any rule keyed on frontmatter scope, or on an `sdd-` name prefix, installs skills the user never chose.

`_shared/` is always installed (`jarvis-cli/internal/agent/install.go:33-34,61`).

### F4 — The statusline consent is the only real schema gap

`statuslineConfirm func() bool` (`jarvis-cli/internal/tui/agent_setup.go:85`) is consumed at `agent_setup.go:145` and built per front-end (`steps.go:1425`, `nontui.go:379`). It is transient interactive consent, never persisted.

Replay needs a tri-state, because "answered no" and "never asked" are different facts even though both resolve to the same action. Two plain booleans suffice: unlike persona in the reference implementation, the zero value here is the safe outcome, so field-presence detection is unnecessary.

Jarvis already contains this pattern internally: `WriteSyncCredentials` uses `autoSync *bool` where `nil` preserves and non-nil forces (`jarvis-cli/internal/config/syncjson.go:18-30`).

### F5 — The ownership model is strong but only wired at install time

`internal/reconcile` implements strict evidence-based ownership:

- `Classify` (`internal/reconcile/reconcile.go:105-118`) returns `proven-jarvis` only when a versioned `Provenance` marker binds the artifact to the current manifest by version, identity, and location on both sides. Names, paths, JSON keys, and references are explicitly rejected as proof (`:44-46`, `:103-104`).
- `Ownership` has three values: `proven-jarvis`, `foreign`, `ambiguous-legacy` (`:19-21`).
- `BuildPlan` has exactly one production call site: `internal/agent/production_bridge.go:465`, inside `BuildProductionReconcileRequest`, documented as deriving the plan "solely from wizard selections and already-rendered managed outputs" (`:436-438`).
- `InventoryProvider` (`internal/agent/inventory.go:10`), the seam for observing on-disk artifacts, has **zero implementations**. `OpenCodeGlobalAdapter.Inventory()` (`opencode_global_adapter.go:109`) returns `([]reconcile.Artifact, error)` — a different signature that does not satisfy it. Inventory is populated only from caller-supplied `output.Existing` (`production_bridge.go:461-463`).

Marker coverage by artifact class:

| Class | Marker | Evidence |
|---|---|---|
| OpenCode global config | Yes | `openCodeProvenance` (`production_bridge.go:218-227`) |
| Rendered instruction outputs | Yes, at install | `FileCompensationStore.Write` (`production_bridge.go:150`) |
| Skills on disk | No | plain `writeFileAtomic(destPath, content, 0644)` (`install.go:83`) |
| Claude MCPs | N/A | native store via `claude mcp add/remove` (`claude.go:229-249`), fixed identities |
| Statusline | No | no marker written |

Consequence: sync cannot use `Classify` for skills or the statusline. There is no marker to classify. Identity-based ownership resolves this without introducing markers.

### F6 — Cloud credentials are outside the replay domain

Credentials live in `~/.jarvis/sync.json`, written at mode `0600` (`internal/config/syncjson.go:72`), holding `APIURL`, `Email`, `Password`, `AutoSync` (`:11-16`). Only three sites write it: the TUI wizard (`tui/steps.go:1455`), the non-TUI wizard (`tui/nontui.go:411`), and `jarvis login` (`cmd/jarvis/cmd_login.go:69`).

`AppConfig.Cloud` holds only `Email` and `SyncConfigured` (`internal/config/config.go:44-47`) — bookkeeping, not the credential.

Sync cannot rewrite the file: doing so requires a password that exists only while the user types it, and sync is non-interactive. The file is not a generated artifact and survives upgrades unaided.

### F7 — Backup machinery exists and is concrete

| Element | Location |
|---|---|
| `BackupStore` | `internal/lifecycle/backup.go:23` |
| Snapshot ID `snap-<unixnano>` | `backup.go:28` |

Targets are currently derived from doctor steps. That couples backup to defect observation, which is the wrong input for a replay command.

## Reference implementation

`gentle-ai` solves the same problem in `internal/cli/sync.go` (1967 lines, commit `0d85ec05`). Patterns worth reusing:

| Pattern | Location |
|---|---|
| Replay manifest separate from user config | `internal/state/state.go:50` |
| `*Configured` flags separating "empty selection" from "legacy file" | `internal/state/state.go:54,61-64` |
| Field-presence detection via custom `UnmarshalJSON` | `internal/state/state.go:114,150-165` |
| Fail-closed state validation before any write | `internal/cli/sync.go:1482-1504` |
| Snapshot before / diff after; no-op when zero changed | `internal/cli/sync.go:1558,1574,1585-1587` |
| Changed paths listed in the report | `internal/cli/sync.go:1895-1901` |
| Component order as a documented contract | `internal/cli/sync.go:321-333` |
| Migration before early return; notice only after durable write | `internal/cli/sync.go:1465-1477,1532-1538` |
| Bookkeeping write under lock, only when changed | `internal/cli/sync.go:1606-1640` |
| Snapshot/rollback preserving symlinks and modes | `internal/cli/sync.go:1256-1264,1563` |
| Post-apply verification naming the retry command | `internal/cli/sync.go:1921-1927` |

The ordering pattern deserves emphasis. The comment at `sync.go:321-333` records a real failure: persona must run before the components that inject content, because those emit substrings colliding with persona's legacy-block fingerprints, and a persona pass running last strips the sections just written. Jarvis has persona, sentinel-delimited instruction layers, and skills that inject markdown, so it is exposed to the same failure class.

Two divergences are deliberate. `gentle-ai` falls back to filesystem agent discovery when state is absent (`sync.go:415-442`) for backward compatibility with pre-state installs; Jarvis has no such debt and must block instead. `gentle-ai` supports flag overrides of persisted selection (`sync.go:366-384`); Jarvis ships no flags in this version.

## Decisions already closed

These were settled with the product owner during the investigation and are recorded as the issue's 13 rules:

1. Ownership by identity, not location. Provenance markers where they exist; membership in a known identity set otherwise.
2. Sync never infers, defaults, or redetects an unpersisted decision.
3. Non-wizard content is preserved byte-for-byte.
4. Render from the installed version's embedded assets only.
5. Idempotency is measured by snapshot/diff, not declared.
6. Fail closed when loading state.
7. Component ordering is a tested contract.
8. Migration runs before any early return; report only after a durable write.
9. Sync writes only bookkeeping, under a lock.
10. Sync never enters the Hive memory domain.
11. No filesystem redetection; block instead.
12. `config.yaml` and `state.yaml` share no field.
13. `sync.json` is read-only for sync.

Plus:

- New store `~/.jarvis/state.yaml` with its own schema version; replay fields move out of `config.yaml` (advancing it to `schema_version: 3`) rather than being copied. Disjoint fields cannot disagree, so no tie-breaking rule is needed.
- The manifest `skills` list must never be filtered on write; it is the only ownership proof for deleting a skill a later version dropped.
- Skill lifecycle: non-interactive skills always install; interactive ones only when the manifest says the user chose them; manifest-known skills absent from the catalog are deleted; skills in neither list are untouchable.
- Sync does not announce newly available optional skills.
- No flags in this version, `--dry-run` included.
- Backup targets come from sync's own plan, reusing the same path list rule 5 already requires.
- Boundary: `reconcile` answers "is it broken?" from doctor observations; `sync` answers "is it stale?" from the manifest plus new assets. Sync uses the `internal/reconcile` package and never `lifecycle.Engine`.
- Plaintext password storage in `sync.json` is parked by explicit product decision (single-user machines, dotfiles not published).

## Key Learnings

1. Jarvis-managed MCP definitions are derived from embedded code rather than persisted user choices, so they need no replay manifest entry.
2. Skill installation optionality is decided by the `interactiveSkillIDs` map, never by the frontmatter `scope` field.
3. The `InventoryProvider` interface in `internal/agent/inventory.go` has zero production implementations today.
4. The statusline consent callback is the only genuinely unpersisted decision blocking deterministic replay.
5. Backup allowed roots are restricted to `~/.claude`, `~/.config/opencode`, and `~/.jarvis` by `isAllowedRoot`.
